**Living with it on a laptop** — the release that came out of actually driving a remote sandy all day: the terminal heals itself after the lid opens, the mouse can reach tmux again, and daemon sessions stop lying about whether they're alive.

## What's new

### The terminal repaints itself after sleep (#37 follow-up)

Close the lid on a Remote-SSH session, open it later, and the Sandy tab used to sit on a frozen pre-sleep frame until you closed and reopened it. The webview now runs a heartbeat, notices the wall-clock jump that means "we were asleep", and asks the host to force a tmux redraw — the screen self-heals within ~10s, no ceremony.

New runbook: [`docs/testing/remote-ssh-reconnection.md`](../testing/remote-ssh-reconnection.md), which separates the three things people conflate — *session persistence* (already automatic via daemon mode; you never lose work), *frozen frame* (this fix), and *sluggish stream* (the transport, below sandy-ui).

### ⌥-drag reaches tmux without giving up text selection

`sandy.terminal.mouseMode: nativeSelection` (the default) deliberately hides mouse tracking from tmux so plain drag selects text — but that also put tmux's own mouse features out of reach: no pane-border resize, no click-to-focus. Now **hold ⌥ and drag** and the gesture is forwarded to tmux as real mouse events, while unmodified drag still selects text. Mirrors the inverse exception `tmux` mode already had.

*Caveat worth knowing:* tmux's resize border is one character cell wide, so grabbing it is fiddly by nature. For precise layout, `Ctrl-b :resize-pane -R 30` or `Ctrl-b :select-layout main-vertical` beat fighting the pixel. (On macOS the default `Ctrl-b Ctrl-→` binding is intercepted by Mission Control — [rappdw/sandy#161](https://github.com/rappdw/sandy/issues/161).)

### Daemon sessions stop misreporting themselves

- **A signalled attach client no longer means "your session died" (#45).** node-pty reports a signal death as exit code 0, which read as "session ended while attached" — so an externally-killed local client painted `[process exited 0]` into a terminal whose host-side session was very much alive. The local `sandy --attach` client is a separate process tree from the daemon container; per sandy's own durable-truth rule, killing it says nothing about the session. It now classifies as *detached*, fails open, and tells you the session persists.
- **Lock liveness comes from the contract, not from us guessing (#42).** We were reimplementing sandy's private lock layout — globbing `.<name>-<8hex>.lock`, parsing the PID, running `kill(pid,0)`. sandy already publishes `lock_holder_alive`, so the tree description, tooltip, and the Remove Lock dialog now state liveness definitively instead of hedging ("*the lock claims to be held by PID N…*" → "*confirmed NOT running. This is a safe stale-lock removal.*").

### A failed launch is no longer a dead end (#49)

`sandy --start` forks a supervisor with stdin on `/dev/null`, so approvals hit during container bring-up couldn't be answered — a workspace containing a symlink launched fine from a shell and failed here with no prompt. That's now fixed **upstream** ([rappdw/sandy#221](https://github.com/rappdw/sandy/issues/221) resolves approvals on the client's tty before forking, and sandy-ui gives `--start` a real pty, so the prompt lands in your tab).

For everything that can still fail, a failed `--start` now offers **"Retry in Foreground"** — one launch on the legacy path, where sandy runs directly on our pty so an answerable prompt can be answered and any other failure surfaces interactively. Deliberately a per-launch bypass, not a settings flip.

The message is chosen from sandy's new `--start` exit table (0 ready / 6 refused / 7 crash-loop / 8 timeout, sandy ≥ 1.8.1) and never asserts a cause it can't back — notably it no longer claims "daemon mode can't prompt", which upstream made false.

### Under the hood

- `test/fixtures/fake-sandy` can now die by signal (#46), so the daemon exit-classification path has real regression coverage instead of a fixture that converted every signal to a numeric exit.
- Unit suite 247 → 282.

**Known / deferred**

- **#43** (feature-detect `--workspace`) and **#44** (machine-readable version) are blocked on their sandy counterparts, [#156](https://github.com/rappdw/sandy/issues/156) and [#159](https://github.com/rappdw/sandy/issues/159).
- **#50** — after a `--start` *timeout* specifically, a foreground retry can hit the legacy orphan modal with text that's wrong in that context.
- **Eternal Terminal was evaluated and rejected** for hard network drops: it didn't beat raw Remote-SSH, because the bottleneck is the overlay network re-establishing and VSCode's own connection timeout — neither of which a tunnel underneath can fix. Daemon mode plus a quick reconnect remains the honest answer. Written up in [`docs/testing/remote-ssh-eternal-terminal.md`](../testing/remote-ssh-eternal-terminal.md).

## Install

```bash
curl -L https://github.com/rappdw/sandy-ui/releases/download/v0.8.1/sandy-ui-0.8.1.vsix -o /tmp/sandy.vsix
code --install-extension /tmp/sandy.vsix
```

Then Cmd+Shift+P → "Developer: Reload Window".
