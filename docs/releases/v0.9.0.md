**Stranger-ready, part one.** Settings Save is back, approvals happen in sandy's own terminal, and sandy-ui no longer reaches into sandy's private files.

0.8.3 was a hotfix to catch up with sandy 2.x. This release makes sandy-ui work the way sandy's maintainer asked consumers to work: through sandy's published commands, never around them.

## What's new

### Settings: Save is back

Saving from the Settings panel was turned off in 0.8.3. It's back on, rewritten ([#53](https://github.com/rappdw/sandy-ui/issues/53)):

- **Only what you change is written.** Settings you didn't touch stay out of your file. Comments, ordering, `export` lines, Windows line endings and file permissions are kept. `.secrets` files are kept at 0600 or tighter.
- **Each setting goes to the right file.** Only secrets go to `.secrets`. 0.8.2 also put ten non-secret settings there, among them `SANDY_ALLOW_NO_ISOLATION` and `SANDY_ALLOW_HOSTS`. sandy reads `.secrets` after `config`, so a copy left there overrides your config. The panel now shows such a setting from where sandy actually reads it and flags it. The next time you save or clear that setting, the stray copy is removed.
- **On/off settings are written the way sandy reads them.** Most sandy switches test for `1`, and only `SANDY_SKIP_PERMISSIONS` tests for `true`. Earlier versions wrote `true`/`false` for every switch, which left e.g. `SANDY_ALLOW_NO_ISOLATION` off while the panel showed it on. If a value in your file can't be read by sandy either way, the panel says so under the control.
- **Clearing a field removes the setting.** Blank secrets still mean "keep the current value".
- **`SANDY_AGENT` lists sandy's agents** as checkboxes and keeps their order. The first agent is your primary one ([#52](https://github.com/rappdw/sandy-ui/issues/52)).
- **Settings types this version doesn't know** render as the simple type sandy says they are (a checkbox or a number field), using sandy 2.8's new `base_type`.

### Approvals: a preview, then sandy asks

Before, sandy-ui showed its own approval dialog and then launched sandy with an override that approved everything it read at that moment. Now sandy-ui approves nothing:

- If the workspace needs approval, a **read-only preview** shows what sandy will ask about, using `sandy --approvals` (sandy 2.7+). That covers privileged settings **with their values** (sandy's own prompt shows names only), a project Dockerfile and its build context, or symlinks sandy will refuse. Secret values are masked.
- **sandy then asks in the terminal** and records your answer itself.
- If you decline something, sandy-ui tells you once the session starts: "running without SANDY_ALLOW_HOSTS". Before, you had no way to know.
- When sandy refuses to start because of a symlink, the message names the symlinks and doesn't offer a retry that can't help.

### Update & Restart

**Update & Restart Session** (right-click a running session) and **Sandy: Update & Restart All Sessions** run `sandy --update-sessions`. They rebuild images and restart sessions onto them ([#36](https://github.com/rappdw/sandy-ui/issues/36)). An attached tab shows "(restarting…)" and reattaches to the new container by itself. Progress goes to the "Sandy Updates" output channel.

### Sandboxes and locks: sandy's commands, not sandy's files

- **Delete Sandbox** runs `sandy --remove-sandbox`. The confirmation shows sandy's own plan, which also removes what sandy keeps beside the sandbox folder. That used to be left behind.
- sandy-ui no longer reads or deletes sandy's lock files. sandy clears stale locks itself on every launch, so the **Remove Lock** action and the "already running — stop it?" dialog are gone. This also fixes a dialog that blamed an interrupted VSCode quit after a timed-out start ([#50](https://github.com/rappdw/sandy-ui/issues/50)).

### Windows and tabs

- **The macOS Window menu sorts by workspace.** sandy-ui now sets VSCode's default window title to start with the workspace name, whatever tab is active. It's only a default: your own `window.title` setting still wins.
- **The terminal no longer loses its bottom rows** (the agent's status line) or comes back too small after you switch to another tab and back ([#55](https://github.com/rappdw/sandy-ui/issues/55)). Redraws after a tab switch, a reattach or waking from sleep now ask sandy's tmux to redraw from its own copy of the screen (`sandy --exec`, sandy 2.7+), instead of briefly resizing the terminal.

### Getting started

The walkthrough links sandy's own guide, says the installer installs sandy's latest release, and warns that the first launch builds images, which can take several minutes.

## Requirements

**sandy 2.6.0 or later**, as in 0.8.3. **sandy 2.8.0 is recommended**: the launch preview and the tmux redraw need 2.7, and settings type fallback uses 2.8. sandy-ui detects each feature from sandy's own flags, so on older sandy those features are simply skipped.

## Under the hood

- The schema cache is keyed on the sandy build that's installed (`sandy --print-version`, plus the binary's size and modification time), not on the version string ([#44](https://github.com/rappdw/sandy-ui/issues/44)). sandy's installer can install many builds with one version number.
- Real `sandy --print-schema` output from the 2.8.0 release is a test fixture beside 2.7.1's.
- CI is green on Linux and macOS again. The integration tests had been matching the tab title from before 0.8.2.
- Dependency updates: vsce 4 (releasing now needs Node 22 or later), electron, esbuild, mocha, vitest, @vscode/test-electron.
- Unit suite 312 → 364.

## Install

```bash
curl -L https://github.com/rappdw/sandy-ui/releases/download/v0.9.0/sandy-ui-0.9.0.vsix -o /tmp/sandy.vsix
code --install-extension /tmp/sandy.vsix
```

Then Cmd+Shift+P → "Developer: Reload Window".
